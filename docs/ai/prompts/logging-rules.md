# 공통 로그 작성 규칙

AI 에이전트가 실제 코드, 문서, 리뷰 결과를 파일로 기록할 때는 이 문서의 규칙을 공통으로 따른다.
이 문서는 사람이 AI 작업 이력을 추적하고, 변경 이유와 결과를 빠르게 파악할 수 있게 만드는 것을 목표로 한다.

## 1. 목적

- 로그의 목적은 AI 작업 이력을 사람이 추적하고 디버깅 가능하게 만드는 것이다.
- 아직 사용자와 충분히 합의되지 않은 아이디어, 검토 중인 대안, 보류된 판단은 확정 로그처럼 남기지 않는다.
- 로그는 "무엇을 했는가"만이 아니라 "왜 그렇게 반영했는가"까지 확인할 수 있어야 한다.

## 2. 저장 위치 규칙

- 작업 로그와 리뷰 로그는 분리해서 저장한다.
- 기본 경로는 아래 형식을 따른다.
  - `logs/ai/YYYY/MM/DD/HH.md`
  - `logs/code-review/YYYY/MM/DD/HH.md`
- 날짜와 시간은 실제 작업이 수행된 로컬 시각 기준으로 기록한다.
- 서로 다른 시간대의 작업은 각각 해당 시간 파일에 기록한다.
- 기존 로그 파일이 있다는 이유만으로 다른 시간대 작업을 이전 파일에 이어 쓰지 않는다.

## 3. 파일명 규칙

- 파일명은 작업이 수행된 시각의 "시간" 단위를 기준으로 정한다.
- 한 시간 단위 로그를 기본으로 하며, 같은 시간 파일에 여러 작업을 누적할 수 있다.
- 파일명은 숫자만 사용해 정렬이 자연스럽게 되도록 유지한다.

### 예시

- `logs/ai/2026/04/09/21.md`
- `logs/code-review/2026/04/09/22.md`

## 4. 작성 형식

- 로그는 반드시 사람이 읽기 쉬운 Markdown 형식으로 작성한다.
- 모든 기록은 제목과 본문 섹션이 분리된 형태로 작성한다.
- 각 작업 기록의 끝에는 반드시 Markdown 구분선 `---` 를 넣는다.
- 같은 파일에 여러 작업을 누적할 때도 각 작업 단위 끝마다 동일하게 `---` 를 넣는다.
- 완료되지 않은 메모를 로그에 남겨야 한다면, 확정 기록과 섞지 말고 상태를 분명히 표시한다.

## 5. 필수 기록 항목

모든 작업 로그와 리뷰 로그에는 아래 항목이 포함되어야 한다.

- 작업 날짜와 시간
- 사용자의 요청 요약
- 사용자와 사전 합의한 핵심 내용
- 실제로 반영한 코드, 문서, 리뷰 변경 사항 요약
- 변경 결과 또는 기대 효과

## 6. 프로젝트 전용 작성 원칙

- 이 프로젝트 로그는 추상적인 회고보다 실제 반영 내용을 우선 기록한다.
- 문서 기준을 참고해 판단한 경우 어떤 문서를 봤는지 함께 남긴다.
- 구현 중 다시 문서를 확인했다면 재확인 이유를 짧게 적는다.
- 테스트, 타입체크, 린트, 수동 확인 중 실제 수행한 검증만 기록한다.
- 검증하지 못한 항목은 생략하지 말고, 못 한 이유를 남긴다.

## 7. 작업 로그 작성 규칙

- 작업 로그는 "요청", "합의", "반영", "결과" 흐름이 보이도록 작성한다.
- 바꾼 파일 목록만 나열하지 말고, 핵심 변경 의도를 먼저 적는다.
- 코드와 문서를 함께 수정한 경우 둘 다 기록한다.
- 사용자 요청과 다르게 조정한 부분이 있다면 그 이유를 남긴다.

### 권장 섹션

- 제목
- 작업 시각
- 요청 요약
- 합의된 범위
- 참고 문서
- 반영 내용
- 검증
- 결과 또는 기대 효과
- 남은 이슈

## 8. 리뷰 로그 작성 규칙

- 리뷰 로그는 발견사항 중심으로 작성한다.
- 문제 없음도 기록할 수 있지만, 그 경우에도 어떤 기준으로 확인했는지 남긴다.
- 가능하면 파일 경로와 영향 범위를 함께 적는다.
- 회귀 가능성, 누락된 테스트, 문서와 구현의 불일치 여부를 우선 기록한다.

### 권장 섹션

- 제목
- 리뷰 시각
- 요청 요약
- 합의된 리뷰 범위
- 참고 문서
- 검토 대상
- 발견사항
- 검증 또는 확인 근거
- 남은 리스크

## 9. 권장 템플릿

### 작업 로그 템플릿

```md
## 작업: 제목

### 작업 시각
- YYYY-MM-DD HH:mm

### 요청 요약
- 사용자가 요청한 내용 요약

### 합의된 범위
- 사전에 확정된 작업 범위

### 참고 문서
- 확인한 문서 경로

### 반영 내용
- 실제 반영한 코드 또는 문서 변경

### 검증
- 실행한 검증 또는 확인한 내용

### 결과 또는 기대 효과
- 변경으로 달라진 점

### 남은 이슈
- 후속 확인이 필요한 내용

---
```

### 리뷰 로그 템플릿

```md
## 리뷰: 제목

### 리뷰 시각
- YYYY-MM-DD HH:mm

### 요청 요약
- 리뷰 요청 내용 요약

### 합의된 리뷰 범위
- 사전에 정한 검토 범위

### 참고 문서
- 확인한 문서 경로

### 검토 대상
- 확인한 파일 또는 변경 범위

### 발견사항
- 버그, 회귀 위험, 누락 사항

### 검증 또는 확인 근거
- 확인 기준, 테스트, 코드 근거

### 남은 리스크
- 추가 확인이 필요한 내용

---
```

## 10. 금지 사항

- "수정함", "확인함"처럼 의미 없는 짧은 문장만 남기지 않는다.
- 검증하지 않은 성공 여부를 완료로 기록하지 않는다.
- 논의 중인 아이디어를 확정 반영처럼 기록하지 않는다.
- 다른 시간대의 작업을 기존 파일에 편의상 이어서 기록하지 않는다.
