# 기능 명세 MD 작성 가이드

이 문서는 `docs/plan/function` 아래에 기능 명세 MD 파일을 작성할 때 사용하는 공통 가이드다.

기준 문서:
- [login-state-management-guid.md](./login-state-management-guid.md)
- [layer.md](../layout/layer.md)
- [design-system.md](../layout/design-system.md)
- [screen-patterns.md](../layout/design-system/screen-patterns.md)

## 1. 문서 목적

기능 명세 MD는 아래 목적을 가진다.

- 기능의 데이터 흐름을 정리한다.
- 컴포넌트, 훅, 서비스, 레포지토리, 서버의 책임을 분리한다.
- 구현 전에 상태, 함수, 타입 계약을 먼저 고정한다.
- 기능에 필요한 디자인 기준 문서를 함께 연결한다.
- 구현자가 문서만 보고도 구조를 바로 잡을 수 있어야 한다.

## 2. 기본 원칙

### A. 작성 원칙

- 한 문서는 하나의 기능만 다룬다.
- 설명보다 책임과 계약이 먼저 보여야 한다.
- 같은 내용은 한 번만 정의하고 나머지는 참조로 연결한다.
- 계층 간 책임이 섞이지 않게 쓴다.
- 디자인 토큰과 화면 패턴은 별도 디자인 시스템 문서를 기준으로 참조한다.

### B. 번호 체계

- 최상위: `## 1.`, `## 2.`
- 두 번째: `### A.`, `### B.`
- 세 번째: `#### I.`, `#### II.`
- 네 번째: `##### a.`, `##### b.`

### C. 네이밍

- 상태명은 역할이 드러나야 한다.
- 함수명은 동작이 드러나야 한다.
- 에러 상태는 범위를 나눠서 적는다.
- 파생 가능한 성공 상태는 중복으로 만들지 않는다.

좋은 예:
- `emailError`
- `passwordError`
- `formError`
- `isFormValid`
- `loginUser`

피해야 할 예:
- `msg`
- `data`
- `flag`
- `result`
- `isLoggedIn`

### D. 표기

- 함수명 설명에는 `()`를 붙인다.
- 값이 없으면 `없음`이라고 적는다.
- 범위는 `public`, `private` 중 하나로 통일한다.
- 타입은 링크로 참조한다.

좋은 예:
- `setEmail()`
- `<code>Promise&lt;<a href="#type-login-result">LoginResult</a>&gt;</code>`
- `success: true`, <code>data: <a href="#type-user">User</a></code>

### E. 계층 책임

- 컴포넌트: 화면 구조, props, 이벤트 연결
- 훅: UI 상태 관리, 입력 검증 연결, 서비스 호출
- 서비스: 입력 검증, 비즈니스 로직, 최종 결과 반환
- 레포지토리: API 요청/응답 처리
- 서버: API 관점 요약, 요청/응답 예시

## 3. 기본 구조

기능 명세 MD는 아래 구조를 기본으로 한다.

```text
## 1. 상태 변수 및 함수 정의
## 목차
## 2. 데이터 흐름
  ### A. 컴포넌트
  ### B. 훅
  ### C. 서비스
  ### D. 레포지토리
  ### E. 서버
## 3. 디자인 참조
```

### A. 목차 규칙

- `## 2. 데이터 흐름` 앞에 `## 목차`를 둔다.
- 목차에는 상위 섹션과 데이터 흐름 하위 계층을 먼저 적는다.

예시:

```md
## 목차

- `1. 상태 변수 및 함수 정의`
  - `A. 타입 정의`
  - `B. 상태 변수 정의`
  - `C. 함수 정의`
- `2. 데이터 흐름`
  - `A. 컴포넌트`
  - `B. 훅`
  - `C. 서비스`
  - `D. 레포지토리`
  - `E. 서버`
- `3. 디자인 참조`
  - `A. 디자인 참조 문서`
```

### B. 데이터 흐름 규칙

- 항상 `컴포넌트 -> 훅 -> 서비스 -> 레포지토리 -> 서버` 순서로 적는다.
- 데이터 흐름 아래에는 참조 문서를 링크로 적는다.

### C. 디자인 참조 규칙

- 기능 문서에서 디자인 토큰과 화면 규칙을 새로 길게 정의하지 않는다.
- 상세 디자인 명세는 `docs/plan/layout/design-system` 아래 문서에서 관리한다.
- 기능 문서에는 해당 기능에 필요한 디자인 문서 링크만 연결한다.
- 기본 기준은 [design-system.md](../layout/design-system.md), [screen-patterns.md](../layout/design-system/screen-patterns.md)다.
- 기능 전용 디자인 문서가 있으면 `docs/plan/layout/design-system/<feature>.md` 형태로 정의하고 참조한다.
- 공통 UI와 공통 레이아웃은 [components-ui.md](../layout/design-system/components-ui.md), [components-layout.md](../layout/design-system/components-layout.md)를 참조한다.
- 오픈 소스 라이브러리 사용 기준도 기능 문서가 아니라 디자인 시스템 문서 쪽에 정의한다.

## 4. 섹션별 작성 기준

### A. 타입 정의

- 많이 참조되는 타입부터 먼저 둔다.
- 공통 타입은 정말 공통으로 쓰이는 것만 남긴다.
- 컴포넌트 props 타입은 컴포넌트 섹션에 둔다.
- 훅 상태/액션 타입은 훅 섹션에 둔다.
- 서비스 결과 타입은 서비스 섹션에 둔다.
- API 응답 타입은 레포지토리 섹션에 둔다.

예시:

````md
<a id="type-user"></a>

##### a. `User`

```ts
type User = {
  id: number;
  email: string;
  name: string;
};
```
````

### B. 상태 변수 정의

권장 표:

| 변수명 | 타입 | 설명 | 초기값 | 사용 컴포넌트 |
| --- | --- | --- | --- | --- |

작성 기준:

- 실제로 state로 저장할 값만 넣는다.
- 파생 가능한 값은 가능하면 독립 state로 두지 않는다.
- 입력 필드 에러와 폼 에러는 분리한다.

### C. 함수 정의

권장 표:

| 함수명 | 시그니처 | 역할 | 사용 컴포넌트 |
| --- | --- | --- | --- |

작성 기준:

- 함수명에는 `()`를 붙인다.
- 상태 변경 함수와 요청 함수를 같이 정리한다.
- 이 표에는 외부 계약만 적는다.

### D. 컴포넌트

권장 구조:

- `#### I. 컴포넌트 구조`
- `#### II. 컴포넌트 타입`
- `#### III. 컴포넌트 정의`

권장 표:

| 컴포넌트명 | 역할 | 사용하는 Hook | 받는 props | 이벤트에서 호출하는 함수 | 관리하는 state |
| --- | --- | --- | --- | --- | --- |

작성 기준:

- 페이지 컴포넌트는 `없음`을 명확히 적는다.
- 입력 컴포넌트는 어떤 state를 표시하고 어떤 함수를 호출하는지 적는다.
- 버튼은 비활성화 조건이 있으면 역할에 포함한다.

### E. 훅

권장 구조:

- `#### I. 훅 타입`
- `#### II. useSomething`

세부 구조:

- `##### a. 훅 요약`
- `##### b. 상태`
- `##### c. 함수`
- `##### d. 동작 규칙`
- `##### e. 상태 갱신 규칙`

권장 표:

| 변수 명 | 범위 | 초기 값 | 역할 |
| --- | --- | --- | --- |

| 함수 명 | 범위 | 받는 props | return 값 | 호출하는 service | 관리하는 state |
| --- | --- | --- | --- | --- | --- |

작성 기준:

- 상태는 실제로 노출하는 값만 적는다.
- 함수는 호출 service와 관리하는 state를 같이 적는다.
- 동작 규칙은 함수별로 나눈다.
- 상태 갱신 규칙은 입력 변경, 성공, 실패, 종료, 초기화를 먼저 적는다.

### F. 서비스

권장 구조:

- `#### I. 서비스 타입`
- `#### II. serviceName`

세부 구조:

- `##### a. 서비스 요약`
- `##### b. 함수`
- `##### c. 동작 규칙`
- `##### d. 반환 규칙`

권장 표:

| 함수 명 | 범위 | 받는 props | return 값 | 호출하는 대상 | 실패 메시지 | 역할 |
| --- | --- | --- | --- | --- | --- | --- |

작성 기준:

- 진입 함수와 검증 함수를 같이 적어도 된다.
- `login()` 같은 진입 함수는 최종 흐름만 적는다.
- 세부 검증 규칙은 `validate*()` 쪽에 둔다.
- 반환 규칙은 함수별로 나눈다.

### G. 레포지토리

권장 구조:

- `#### I. API 타입`
- `#### II. repositoryName`

세부 구조:

- `##### a. 레포지토리 요약`
- `##### b. 함수`
- `##### c. 요청 규칙`
- `##### d. 동작 규칙`
- `##### e. 반환 규칙`

권장 표:

| 함수 명 | 받는 props | return 값 | 호출하는 API | 역할 |
| --- | --- | --- | --- | --- |

| 항목 | 내용 |
| --- | --- |

작성 기준:

- 요청 규칙에는 메서드, 경로, 요청 본문을 적는다.
- 레포지토리는 API 요청/응답 처리만 적는다.

### H. 서버

서버 섹션은 이름은 서버지만, 내용은 API 관점으로 간결하게 적는다.

권장 구조:

- `#### I. 기능명 API`
- `##### a. API 요약`
- `##### b. 요청 본문 예시`
- `##### c. 응답 예시`

응답 예시는 아래처럼 묶는다.

```md
##### c. 응답 예시

###### 1. 성공 응답 예시
###### 2. 실패 응답 예시
###### 3. 서버 에러 응답 예시
```

### I. 디자인 참조

권장 구조:

- `## 3. 디자인 참조`
- `### A. 디자인 참조 문서`

작성 기준:

- 기능 문서에는 디자인 문서 링크만 남긴다.
- 디자인 상세는 `docs/plan/layout/design-system` 안에서 관리한다.
- 토큰, 무드, 상태 기준은 [design-system.md](../layout/design-system.md)를 참조한다.
- 화면 조합 규칙은 [screen-patterns.md](../layout/design-system/screen-patterns.md)를 참조한다.
- 공통 UI/레이아웃은 [components-ui.md](../layout/design-system/components-ui.md), [components-layout.md](../layout/design-system/components-layout.md)를 참조한다.
- 기능 전용 디자인 문서가 있으면 함께 링크한다.

권장 표:

| 구분 | 문서 | 역할 |

## 5. 중복 제거 규칙

- 공통 타입은 한 번만 정의하고 링크로 참조한다.
- 상세 검증 규칙은 `validate*()` 함수 아래에만 둔다.
- 요청 함수는 최종 성공/실패만 적는다.
- 파생 가능한 상태는 따로 저장하지 않는다.
- 같은 의미의 상태가 두 개 보이면 하나는 없앨 수 있는지 먼저 확인한다.

## 6. 체크리스트

문서를 마무리하기 전에 아래를 확인한다.

- 상태 변수 정의와 훅 상태 표가 같은 이름을 쓰는가
- 함수 정의와 훅 함수 표가 같은 이름을 쓰는가
- 컴포넌트 정의 표의 state와 실제 훅 state가 일치하는가
- 실시간 검증 에러와 요청 실패 에러가 분리되어 있는가
- 성공 상태를 중복으로 관리하지 않는가
- 서비스와 레포지토리의 책임이 섞이지 않았는가
- 타입 참조 링크가 올바르게 연결되어 있는가
- 헤더 번호 체계가 맞는가
- 목차가 `데이터 흐름` 앞에 들어가 있는가
- 디자인 참조 문서가 연결되어 있는가
- 기능 문서에서 디자인 내용을 중복 정의하지 않았는가
- 상세 디자인이 `docs/plan/layout/design-system` 아래 문서에 정의되어 있는가
